# Этап 1 — Отчёт

## Что готово

### Сервис шифрования (`backend/app/services/`)
- `encryption_service.py` — абстрактный класс `EncryptionService` с восемью методами: `encrypt`, `decrypt`, `derive_user_key`, `store_session_key`, `get_session_key`, `revoke_session_key`, `encrypt_with_key`, `decrypt_with_key`. Все методы — async, все принимают `user_id` (где применимо), сигнатуры финальные (не изменятся на этапе 7). Также определены два исключения: `EncryptionError` и `SessionKeyNotFoundError`.
- `encryption_identity.py` — `IdentityEncryptionService`. Возвращает входные значения без изменений; `derive_user_key` отдаёт фиксированный 32-байтный ключ; `get_session_key` тоже отдаёт этот же ключ (чтобы сервисы, опирающиеся на «ключ существует», работали в identity-режиме без условных веток). Каждый вызов логируется на DEBUG **без plaintext и ключей** — только `user_id` и метаданные.
- `encryption_aesgcm.py` — `AESGCMEncryptionService`. Все методы поднимают `NotImplementedError("Реализация AES-256-GCM включается на этапе 7")`. Зависимости `cryptography` и `argon2-cffi` пока **не** добавлены в `pyproject.toml` — это сделаем на этапе 7 вместе с реальной реализацией.

### DI (`backend/app/dependencies.py`)
- `get_encryption_service()` — FastAPI dependency, возвращает singleton (`@lru_cache(maxsize=1)`).
- При `ENCRYPTION_PROVIDER=identity` отдаёт `IdentityEncryptionService`.
- При `ENCRYPTION_PROVIDER=aesgcm` поднимает явный `NotImplementedError` с текстом «wired on stage 7». Это нужно, чтобы случайно поставленный `aesgcm` в `.env` упал на старте, а не молча проигнорировал шифрование.
- При неизвестном значении — `ValueError`.
- Хелпер `reset_encryption_service_cache()` — для тестов, которые меняют провайдер на лету.

### Тесты (`backend/tests/unit/`)
11 unit-тестов, не требуют ни БД, ни Redis:
- `test_encryption_identity.py` (6 тестов): round-trip, пустая строка, длина ключа = 32 байта, lifecycle сессионного ключа, `encrypt_with_key/decrypt_with_key` round-trip, отсутствие plaintext в DEBUG-логах.
- `test_encryption_aesgcm_stub.py` (3 теста): все методы поднимают `NotImplementedError`, сообщение содержит «этапе 7», класс полностью реализует интерфейс (можно `isinstance`-проверить).
- `test_encryption_factory.py` (2 теста): фабрика возвращает identity и падает на неизвестном провайдере.

### Документация
- `docs/ENCRYPTION.md` — пять разделов: зачем, целевая архитектура (этап 7+), что сделано сейчас, план активации на этапе 7, как использовать в коде.
- `docs/ETAP_1_REPORT.md` (этот файл).

## Объяснение для заказчика (зачем заглушка)

Шифрование медицинских данных — самый чувствительный кусок системы. Если включить его сразу на этапе 1, любая последующая правка модели (а на этапах 2–6 мы будем активно её менять) превращается в неприятный квест: миграция должна расшифровать → изменить → перешифровать. Поэтому мы заранее построили **контракт** шифрования (интерфейс) и **временную честную пустышку** (identity). Весь код, который будет писаться на этапах 2–6, уже выглядит так, как если бы шифрование работало по-настоящему — те же вызовы, те же сигнатуры, те же типы данных. Просто внутри пустышка возвращает то же, что приняла. На этапе 7 мы заменим пустышку на настоящий AES-256-GCM, и ни одна строчка в остальном коде не поменяется. Это стандартный приём в архитектуре безопасности: чем позже мы внедряем дорогую механику, тем меньше шансов её сломать неосторожным рефакторингом.

## Подтверждение совместимости с этапом 7

Гарантирую, что переход с identity на aesgcm на этапе 7 НЕ потребует изменений в коде других модулей. Конкретно:

1. **Сигнатуры всех восьми методов финальны.** На этапе 7 мы только заполняем тела `AESGCMEncryptionService.*`.
2. **Только конфиг.** Активация — это `ENCRYPTION_PROVIDER=aesgcm` в `.env` + новый сервис `redis_keys` в `docker-compose.yml`.
3. **Inject через `Depends(get_encryption_service)`.** API-роуты и сервисы получают абстракцию, а не конкретный класс — фабрика выбирает реализацию централизованно.
4. **Логирование без секретов уже сейчас.** Сейчас identity-логи на DEBUG показывают только `user_id` и длину строки. Тот же контракт сохранится на этапе 7.
5. **Тесты не зависят от реализации.** Round-trip-тесты (`test_encryption_identity.py`) можно прогнать и на AES-реализации — они оперируют только публичным интерфейсом.

## Архитектурные решения

1. **`get_session_key` возвращает константу, а не `None`.** В identity-режиме «ключа нет» — это потенциальный путь ошибок: сервис, написанный с проверкой `if key is None: raise`, начнёт падать на ровном месте. Чтобы сервисы на этапах 3–6 писались естественным потоком (без специальных веток для identity), пустышка отдаёт корректный 32-байтный ключ всегда. На этапе 7 поведение станет настоящим.
2. **Async-методы даже у identity-реализации.** Все методы остаются `async`, чтобы код, написанный сейчас как `await encryption.encrypt(...)`, не пришлось переписывать на этапе 7. Накладные расходы на `async` без I/O — пренебрежимо малы.
3. **`@lru_cache(maxsize=1)` на фабрике вместо синглтона на уровне модуля.** Преимущество — фабрика остаётся «чистой» функцией, чьё значение можно сбросить в тестах через `cache_clear()`. Помощник `reset_encryption_service_cache()` экспортирован специально для этого.
4. **AESGCMEncryptionService уже наследуется от `EncryptionService` и проходит `isinstance`.** Это позволяет писать тесты, которые работают с любой реализацией интерфейса — гарантия, что мы не «забыли» какой-то метод при переходе на этап 7 (третий тест в `test_encryption_aesgcm_stub.py`).
5. **Зависимости `cryptography`/`argon2-cffi` пока НЕ в `pyproject.toml`.** Это сознательно: меньше пакетов в контейнере = меньше CVE-surface на этапах 0–6 в dev-режиме. Добавим в одной коммит-серии с реальной реализацией на этапе 7.
