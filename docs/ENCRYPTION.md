# Шифрование медицинских данных

> Статус: AES-256-GCM активен с Шага E (Спринт 2). Прежняя identity-stub
> архитектура осталась для тестов/dev — переключается через
> `ENCRYPTION_PROVIDER=identity|aesgcm` в .env.

## 1. Зачем

Согласно §1.3 ТЗ, главная ценность МедАрхива — приватность. Все медицинские
данные пользователя должны быть нечитаемы для третьих лиц, **включая
администратора сервера**. Конкретно это значит: сами по себе данные в БД
лежат в виде шифротекста; ключ для их расшифровки нигде не сохраняется на
постоянное хранение, а живёт только в памяти Redis на время сессии. Без
пароля пользователя ни злоумышленник, получивший дамп БД, ни администратор
сервера не могут прочитать содержимое.

Это вторая линия защиты помимо обычных мер (HTTPS, JWT, bcrypt-хеши
паролей, изоляция данных по `user_id`). Первая линия защищает от внешнего
взлома; шифрование защищает от компрометации самой инфраструктуры.

## 2. Целевая архитектура (этап 7+)

### 2.1. Ключи

```
Пароль пользователя (никогда не уходит за пределы process памяти)
        │
        ▼ Argon2id KDF (соль из users.encryption_salt, 32 байта)
        │
        ▼ 32-байтный мастер-ключ
        │
        ├── шифрует 🔒-поля в БД (AES-256-GCM)
        ├── живёт в redis_keys на время refresh-токена
        └── зашифрованная копия в users.recovery_master_key
              (ключом, выведенным из резервного кода)
```

Параметры Argon2id (по OWASP ASVS L3, ориентируемся): `memory_cost=64 MiB`,
`time_cost=3`, `parallelism=4`. Финальные параметры будут зафиксированы и
закоммичены на этапе 7 после бенчмарка на целевом железе.

### 2.2. Шифрование данных

- Алгоритм: AES-256-GCM.
- Формат на диске: `base64(nonce(12 байт) || ciphertext || tag(16 байт))`.
- Каждое поле шифруется отдельно с **уникальным nonce** (CSPRNG).
- Поля, помеченные 🔒 в спецификации §5, проходят через `encrypt(...)` в
  сервисе до записи в БД и через `decrypt(...)` после чтения.

### 2.3. Жизненный цикл сессии

| Событие | Что происходит с ключом |
|---|---|
| Регистрация | Создаётся `encryption_salt = secrets.token_bytes(32)`; пароль хешируется bcrypt'ом отдельно от KDF. |
| Логин | Argon2id выводит мастер-ключ → `redis_keys.set(user:{id}:{session_id}, key, ex=refresh_ttl)`. |
| Refresh access-токена | Refresh-токен ротируется; ключ в `redis_keys` пересоздаётся (TTL обнуляется). |
| Logout | `redis_keys.delete(user:{id}:{session_id})`. |
| Истечение refresh-токена | TTL в `redis_keys` истекает автоматически. |

### 2.4. Восстановление

При генерации резервного кода:
1. Случайные 16 байт → отображаются пользователю как BIP-39-подобная фраза.
2. Argon2id выводит из этого кода ключ восстановления.
3. Действующий мастер-ключ шифруется этим ключом восстановления.
4. Результат сохраняется в `users.recovery_master_key`.

При использовании резервного кода пользователь вводит фразу, мы выводим
ключ восстановления, расшифровываем `recovery_master_key`, получаем
оригинальный мастер-ключ и кладём в `redis_keys`. Пароль пользователя
полностью сбрасывается отдельной процедурой.

## 3. Этап 3 — первая проверка боем

С этапа 3 `EncryptionService` впервые активно используется бизнес-логикой:
`PatientProfileService`, `ChronicConditionsService`, `AllergiesService`,
`FamilyHistoryService` шифруют все 🔒-поля перед записью в БД и
расшифровывают на чтение. Round-trip-тесты (`backend/tests/integration/test_profile.py`)
подтверждают, что данные возвращаются ровно такими, какими были записаны —
интерфейс работает корректно. На этапах 0–6 это identity-passthrough, но
формат вызовов сохранится при переходе на AES-GCM (этап 7): сами сервисы
менять не придётся.

  сигнатурами. Сервисы на этапах 3–6 будут писать код **уже так, как если
  бы данные шифровались**, не зная о том, что под капотом identity-заглушка.

  Никогда не логирует ни plaintext, ни ключи.
- `AESGCMEncryptionService` — каркас. Все методы поднимают
  `NotImplementedError("Реализация AES-256-GCM включается на этапе 7")`.
  Зависимости `cryptography` и `argon2-cffi` в `pyproject.toml` пока **не
  добавлены** — добавим на этапе 7 вместе с реальной реализацией.
- `app/dependencies.py::get_encryption_service` — фабрика, выбирает
  реализацию по `ENCRYPTION_PROVIDER`. На этапе 1 значение — `identity`.
- Unit-тесты: 11 штук покрывают round-trip, пустую строку, длину
  выведенного ключа, lifecycle сессионного ключа, отсутствие plaintext в
  логах, NotImplementedError у каркаса и поведение фабрики.

## 4. Что будет на этапе 7

Пошаговый план активации настоящего шифрования:

1. **Добавить зависимости:** `cryptography`, `argon2-cffi`.
2. **Добавить второй Redis:** сервис `redis_keys` в `docker-compose.yml`
   **без persistence** (`--save "" --appendonly no`).
3. **Реализовать `AESGCMEncryptionService`:**
   - `derive_user_key` → Argon2id (параметры из `Settings`).
   - `encrypt` / `decrypt` → AES-256-GCM с генерируемым nonce.
   - `store/get/revoke_session_key` → `redis.asyncio` поверх отдельного клиента.
   - `encrypt_with_key` / `decrypt_with_key` — то же AES-GCM, но с переданным ключом.
4. **Обновить фабрику:** при `ENCRYPTION_PROVIDER=aesgcm` инстанцировать
   `AESGCMEncryptionService(redis_keys_client=..., argon2_params=...)`.
5. **Расширить `auth_service`:** при логине — `derive_user_key` →
   `store_session_key`. При refresh — пересохранять ключ с новым TTL. При
   logout — `revoke_session_key`.
6. **Recovery:** при первой настройке сгенерировать резервный код,
   зашифровать им мастер-ключ, положить в `users.recovery_master_key`.
7. **Миграция данных:** не требуется (данные на этапах 0–6 хранятся в
   plaintext в `Text`/`LargeBinary` колонках; на этапе 7 нужно либо
   перешифровать существующие записи демо-юзера, либо просто их удалить).
8. **Переключение:** `ENCRYPTION_PROVIDER=aesgcm` в `.env`. **Никаких
   изменений в коде сервисов и API не требуется.**
9. Тесты: добавить интеграционный тест на полный round-trip через AES; на
   потерю сессионного ключа (`SessionKeyNotFoundError`); на восстановление
   через резервный код.

## 5. Как использовать в коде (этапы 3–6)

В сервисах принимай `EncryptionService` через DI и вызывай его до записи
в БД и после чтения:

```python
from sqlalchemy.ext.asyncio import AsyncSession

from app.services.encryption_service import EncryptionService


class PatientProfileService:
    def __init__(self, encryption: EncryptionService, db: AsyncSession):
        self._encryption = encryption
        self._db = db

    async def save_profile(
        self,
        user_id: int,
        first_name: str,
        anamnesis: str,
    ) -> None:
        encrypted_first_name = await self._encryption.encrypt(first_name, user_id)
        encrypted_anamnesis = await self._encryption.encrypt(anamnesis, user_id)
        # ... запись в БД зашифрованных значений
```

Правила:

- **Никогда** не сравнивай шифротексты на равенство при поиске. Шифр
  AES-GCM с уникальным nonce даёт разные ciphertext для одинаковых
  plaintext. Поиск по полному совпадению строится либо через дешифровку
  после выборки, либо через отдельный детерминированный hash-индекс
  (на этапе 8 при OCR — см. §6.11.1 ТЗ).
- **Никогда** не пиши в лог `plaintext`, `ciphertext`, ключи. Метаданные
  (`user_id`, длину строки) — можно.
- В API-схемах (Pydantic) — поля идут **расшифрованными**. Шифрование —
  чисто внутри слоя services перед БД.
