# Руководство администратора МедАрхив

Документ описывает, как назначить первого администратора, какие
админские возможности доступны, и как делегировать роль другим
пользователям без прямого доступа к БД.

## Назначение первого администратора

1. В файле `.env` укажи email будущего администратора:
   ```env
   INITIAL_ADMIN_EMAIL=admin@yourdomain.tld
   ```
2. Перезапусти стек: `docker compose up -d --build`.
3. Зарегистрируйся через UI как обычный пользователь с этим email.
   - При регистрации сервер увидит совпадение и проставит `role=admin`
     для этого пользователя.
   - Сравнение case-insensitive (`Admin@Yourdomain.TLD` == `admin@yourdomain.tld`).
4. Подтверди email и зайди в приложение.
5. Откорой `/api/v1/admin/me` (через DevTools или curl) — должен вернуть
   `200 OK` с полем `"role": "admin"`. Если возвращает `403`, проверь,
   что `.env` действительно содержит правильный `INITIAL_ADMIN_EMAIL`
   и сервер перезапущен.

> ⚠️ `INITIAL_ADMIN_EMAIL` влияет только на **новых** пользователей.
> Если ты сначала зарегистрировался как обычный USER, а потом прописал
> `INITIAL_ADMIN_EMAIL=` — роль не изменится. В этом случае назначь
> роль вручную:
> ```sql
> UPDATE users SET role='admin' WHERE email='admin@yourdomain.tld';
> ```

## Что может администратор сейчас (Спринт 1)

- ✅ `GET /api/v1/admin/me` — проверка, что у тебя есть админская роль
- ✅ Все эндпоинты обычного пользователя (своё пространство данных)
- ✅ Email-верификация работает через настоящий SMTP (см. [DEPLOY.md](DEPLOY.md))
- ✅ Управление инвайт-кодами и режимом регистрации (см. ниже)

### Управление режимом регистрации

```bash
# Получить текущий режим
GET /api/v1/admin/settings/registration-mode

# Переключить (mode: "closed" | "invite_only" | "open")
PATCH /api/v1/admin/settings/registration-mode
Content-Type: application/json
{"mode": "invite_only"}
```

Стартовый режим после миграции — `invite_only`. Бутстрап-админ
(`INITIAL_ADMIN_EMAIL`) всегда может зарегистрироваться без инвайта,
даже в режиме `closed`.

### Инвайт-коды

```bash
# Создать инвайт-код (срок жизни 7 дней)
POST /api/v1/admin/invites
{"note": "alpha tester #1"}   # note опционально

# Ответ:
{"invite": {"id": 1, "code": "LZK7XV6FJN9PM3B8...", "status": "active", ...}}

# Список всех кодов
GET /api/v1/admin/invites

# Отозвать неиспользованный код
DELETE /api/v1/admin/invites/{id}
```

Каждый код одноразовый. После использования код больше не работает,
но пользователь продолжает пользоваться приложением без ограничений
(даже когда срок жизни кода истёк бы).

Статусы кодов:
- `active` — можно использовать
- `used` — уже использован пользователем (виден email в `used_by_email`)
- `revoked` — отозван админом
- `expired` — прошёл срок жизни без использования

## Что появится позже

| Шаг | Возможности |
|---|---|
| G (Тикеты) | Просмотр, ответ, изменение статуса тикетов поддержки |
| H (UI) | Полноценная админ-панель во frontend: дашборд, пользователи, инвайты, тикеты |
| I (Telegram) | Уведомления о новых регистрациях, тикетах, ошибках в отдельный admin-бот |

## Принцип: админ НЕ видит медданные

По архитектуре приложения (см. [ENCRYPTION.md](ENCRYPTION.md)) ключ
шифрования медицинских данных каждого пользователя выводится из его
**пароля**. Администратор технически НЕ может расшифровать чужие
анализы, профиль, переписку с ИИ. Это сохранится после включения
AES-режима (Шаг E).

Что админ видит про пользователей:
- ✅ email, username, дата регистрации, последний вход, статус, роль
- ✅ агрегированные метрики (количество анализов, размер использованного диска)
- ❌ содержимое анализов, профиля, чата с ИИ, файлов

## Безопасность

- Никогда не делись ссылкой `/api/v1/admin/*` с обычными пользователями —
  ничего страшного, они получат 403, но это раскрывает существование роли.
- Если подозреваешь компрометацию админского аккаунта — смени пароль
  немедленно через UI. После Шага F (мнемоника) — обязательно
  сгенерируй новую резервную фразу.
- Не давай админскую роль больше чем 2-3 людям. Для аудита и
  расследования инцидентов admin-операции логируются с user_id админа.
